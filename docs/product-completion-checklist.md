# Finite product completion checklist

Status: planning only. The final pilot does not authorize production implementation, final marketplace identities or publication. Do not add another pilot round automatically. Each item closes with recorded evidence or an explicit unresolved requirement; missing evidence never passes. Do not remove a requirement to declare completion.

1. [ ] **Approve the evidence-based design.** Choose the smallest adequate chat-only policy and thin host-specific delivery; approve the exact scope and known limits before production edits. No requirement to outperform identical manual instructions. Document installation/automatic application benefits separately from communication-efficacy claims.
2. [ ] **Agree compatibility and release-test scope/budget.** Name supported host/version/OS combinations, including intended Codex CLI/desktop and owner-run Claude routes; define subscription/model sessions, child/reviewer/failure counts, offline checks and stopping rules. Source-only or deferred integrations remain unverified; any exclusion needs an explicit decision. No direct Claude execution by this agent.
3. [ ] **Define audience and instruction precedence.** Ordinary human chat only; preserve explicit requested depth and host/user preferences. Cover resumed chats, child inheritance, automation/nonhuman callers and unknown audiences without assuming a user-role message is human. Resolve unsupported boundaries before claiming support.
4. [ ] **Choose distribution and identities.** Decide dedicated/shared catalog and exact IDs only with owner approval. Record marketplace restrictions independently from technical host feasibility. Do not promise directory eligibility for a hook route that requires manual installation.
5. [ ] **Implement the approved minimal runtime.** Only necessary policy and host metadata/loader files, no evaluator, extra model call, proxy, output rewriting, telemetry or development fixtures in the installable artifact. State actual dependencies, byte count, latency and permissions; do not claim zero overhead without evidence.
6. [ ] **Test host loading and lifecycle.** On every agreed compatibility target verify exact installed bytes, one intended activation, fresh and resumed conversations, startup failures and unrelated plugin coexistence. Verify actual loading, not inventory alone.
7. [ ] **Test ordinary communication and depth.** Use separately agreed untouched release tasks, including realistic follow-ups, nontechnical and technical audiences, necessary long answers, uncertainty and useful versus distracting progress. Reuse automated preservation checks and independent blinded review; owner grading optional. Pilot samples are not a release holdout.
8. [ ] **Test protected generated work.** Execute actual generated code/tests where required; inspect real reports, documentation, comments, copy-ready text, exact quotations, structured/tool output and persistent memory. Verify semantic content/format and requested detail separately from chat preference, including failures and honest verification status.
9. [ ] **Test inter-agent scope with adequate evidence.** Observe actual parent instructions and child responses on each supported route and inspect saved work. Existing unreadable instructions remain unverified. Agree a supported verification approach before any affected test; do not repeat the blocked capture path or silently substitute another orchestration setup.
10. [ ] **Test installed-enabled, installed-disabled and absent.** Use isolated clean profiles, same approved tasks and unrelated preference sentinels. Disabled/absent must stop applying the candidate; enabled must retain work and essentials. Include manual minimal instruction and native concise comparator where available, without inventing missing native modes.
11. [ ] **Test installation and upgrade.** Install the exact packaged artifact through intended supported routes, check dependencies/error handling, preserve unrelated settings, and document ownership/version behavior. Avoid global overrides and unrequested preference replacement.
12. [ ] **Test disabling, re-enabling and removal.** Verify effect stops, unrelated preferences remain intact and removal leaves no active hooks/styles or secret copies. Document whether existing chat context retains inherited text and how to start a clean chat; do not promise retroactive removal of context.
13. [ ] **Finish user-facing docs and rollback.** Explain what changes, protected surfaces, supported targets, install/enable/disable/remove steps, dependencies and honest limitations with practical recovery steps. Keep implementation details out of ordinary product flows unless needed for a decision.
14. [ ] **Prepare license and provenance.** Select an owner-approved license; record upstream attribution and third-party restrictions for every distributed file. Complete this before publication, rather than inferring rights from public availability.
15. [ ] **Audit exact release files and all Git history.** Review secrets, personal/private information, commit-author contact metadata, licensing/copyright and accidental fixtures/logs. Resolve the configured personal-email versus GitHub noreply choice before public history is exposed; no silent history rewrite.
16. [ ] **Obtain release approval of the exact revision/artifact.** Present compatibility, scope preservation, lifecycle results, package contents/hashes, claims and unresolved requirements. Necessary release testing has its own agreed scope and budget. Failures require correction within that agreement or a new decision, not weakened criteria.
17. [ ] **Publish only after approval.** Reconfirm repository ownership/existence, create or use PUBLIC `Shilo/SimplySay`, push only reviewed history/artifacts, verify public contents and provide the URL. Final marketplace names and marketplace publication require their own approved identity/scope.
