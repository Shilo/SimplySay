## Question and candidate

Does an original instruction to construct concrete, reader-appropriate explanations improve final answers, while a separate before-completion gate reduces optional progress narration, without reducing requested work or detail?

Screen [concrete.v1](../experiments/reader-v1/candidates/concrete.v1.txt), based on the independent instruction challenge. Its new final-answer mechanism names actors/actions/consequences and explains unfamiliar terms when needed, rather than equating simplicity with deletion. The progress gate applies only during work; completed answers retain their reasoning and requested depth. V5 remains an unrun, narrower progress-only alternative; no competitor policy, persona, code-minimization rule or fixture-specific noun enters this policy. Test another candidate only when observed evidence gives it a distinct purpose.

Risks: defining familiar terms can clutter an expert answer; concrete wording can lose useful precision; “needed before completion” can be ignored or suppress a useful early warning. The host still requires openings and periodic updates. A policy can improve their content without eliminating their required presence. Actual progress, final answers and protected deliverables must be judged separately.

The reference delta audit supports feasibility of style changes, not an efficacy claim. Several comparisons use system-prompt overrides rather than shipped installation. Ponytail's published shorter-answer result did not beat its untreated baseline in blinded reply preference. We import neither policies nor its multi-model evaluation machinery. No new reference arm answers the current primary question better than an original candidate under the actual host.

## Cases and matched conditions

Use the independent case designer's two three-turn conversations:

- A volunteer coordinator asks about sync versus a retained backup, requests a practical recommendation with uncertainty, then asks a simple completion-time question. This includes nontechnical explanation, recommendations, follow-ups and an already-clear opportunity.
- A maintainer requests a real built-in-Node work-order merge repair and meaningful tests, then a worked technical explanation, then complete saved handoff/copy-ready staff text and an exact original-note copy. This exercises requested depth, code/docs/files and natural tool-work progress. No artificial delay, unnecessary tool sequence or verbose-baseline instruction.

Run each absent, installed-enabled and installed-disabled: six fresh response contexts, 18 task starts. All tasks, fixtures, audience framing, tools, model/effort/host settings and user preferences match within a triad. Preserve every outcome. Start with the first absent/enabled pair and inspect its capture, actual outputs and any observed scope/access issue before launching the rest. Do not tune policy/cases inside a frozen unit. Already-good baseline answers remain in the record.

Use the existing 0.165.0-alpha.1.2 Windows app-server backend, gpt-6.1-sol/xhigh/default route and isolated profiles. The current binary hash matches the historical pinned version. This is a backend behavior test, not desktop UI/notification coverage. No system prompt replacement, host requirement removal, app access, delegation, networked task tool or personal project. Actual native installation and disabling use the same four-file package and controls. General delivery research is not repeated; changed-candidate bytes and supported context are bound to each new run. Persisted context does not prove model attention.

## Three separate records

1. **Delivery:** actual installed bytes, enabled/disabled state, hook evidence, and supported developer/user message role/order/retention; no hidden reasoning or outgoing-wire inference. Controls have no candidate activation/text. Do not confuse a manual comparator with the installed package.
2. **Obedience:** inspect whether the intended patterns occur in actual human chat (concrete referents/needed term explanations, requested detail, no optional narration), whether host requirements remain and whether work surfaces are preserved. These observations do not themselves establish reader benefit.
3. **Usefulness:** two fresh blinded independent reviewers, one task each, receive all chronological requests/replies/progress, actual files/copy and execution evidence. Opposite sides/order, no treatment/policy labels or earlier judgments. Readability/clarity, relevance, jargon, filler, repetition, unnecessary explanation and optional progress are separate goals. The extra explanation/tie notes use a thin companion to the existing validator, not a new framework or runtime service.

Reviewer controls retain the four historical controls and add realistic truthful-but-unneeded updates, plausible overexplaining, unexplained terms and a necessary-interruption counterexample. Eligibility is recorded per claim; failed/unknown/missing controls cannot substantiate that goal. Exact quotes belong in evidence, explanatory missing-content descriptions in issues. Test the field contract locally before grading. Keep raw failures and any transparent meaning-preserving format recovery.

## Interpretation and progression

- Request-derived deterministic checks and actual work quality are independent of style. Run meaningful frozen code probes only after inspecting generated source; distinguish evaluator execution from the subject's actual tests. No requirement for identical hidden reasoning or identical tool sequences.
- A goal improves only with concrete, calibrated independent evidence on that goal and surface. Progress-only preference does not prove better finals; shorter answers/messages do not prove easier reading. Already-satisfactory ties are acceptable; ties retaining the problem leave it unsolved; inadequate evidence remains unknown. Shared baseline errors remain failures without automatic policy attribution.
- A promising candidate needs useful final-answer gain where a problem occurs and a progress gain where optional narration occurs, without lost essentials/requested depth/work or a worsened goal. Both eligible reviewers must agree on the same claimed goal/surface for that gain; do not turn preferences on different goals into a shared goal claim. A missing opportunity is untested, not passed. Do not require a gain in an already-clear segment.
- If the candidate does nothing where problems occur, diagnose recorded delivery, applicability, wording/adherence, competing guidance, task opportunity and calibration before revising. No automatic repeats of unchanged wording. If the baseline meets a goal already, do not hunt for an artificially worse baseline.
- If promising, freeze a subsequent validation unit on genuinely unused conversations and matched repetitions. Keep validation separate, record exposure, and never tune on it while calling it untouched. The existing two sealed cases remain unopened during this development unit; their suitability is not assumed. No reliability claim from this one unit.

## Usage and limits

Preparation: three independent development conversations; six tasks including runner verification, case/evaluation implementation and a separate independent evaluation-contract verification follow-up. Unit 1: six response conversations/18 tasks and two fresh reviewer conversations/two tasks. Expected cumulative new-phase use after this unit: **11 conversations/26 task starts**. Any further implementation/verification task needs a separately recorded concrete purpose. Failures and diagnostics are counted. The historical additional phase remains 25 conversations/78 tasks; its former caps are superseded, not erased.

Native failures stop the affected comparison. No retry/replacement for an unfavorable style result or failed substantive calibration; save responses for offline diagnosis or reviewer-only reassessment when warranted. Provider permission/limit exhaustion stops affected launches without a paid fallback. Do not query repeatedly or change billing/access. New helper/reviewer work must have a recorded purpose; thorough authorization does not justify aimless repetition.

No native inter-agent route is tested in this unit; opaque incoming instructions remain unverified. Other models/apps, full desktop behavior, lifecycle/removal, native concise/manual comparators and release scope remain open as appropriate. All production architecture, final identities and publication still require approval.
