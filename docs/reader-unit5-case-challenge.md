### D: choosing photo copies for a display and website

One normal `image-notes.md` production note supplies: original JPEG 4000 × 3000 pixels; downsampled web JPEG 1000 × 750; same framing, both with a 300-pixels-per-inch metadata label. The website accepts images up to 1200 pixels on the longest edge. The display image area is 10 × 7.5 inches, and its stated production requirement is at least 240 image pixels per printed inch. Changing only the metadata label does not resample pixels. Preserve the original; no sample print has been inspected. The pack contains notes about the images, not image files to edit.

Exact turns:

1. “Read image-notes.md. I’m preparing photos for our community display and website. Both files say 300 dpi, but the web copy looks softer. What does that label tell me, and which copy should I use for each job?”
2. “If I change only the web copy’s label from 300 to 600 dpi, will that fix the display print?”
3. “Please work through how you reached that recommendation. Show the pixel dimensions needed for the 10 by 7.5 inch print and the pixel density each copy provides at that size. Explain the difference between changing the label, reducing the image, and enlarging it. We may later need a 10 by 8 inch borderless layout; explain the choices that would create rather than silently stretching the photo. I need to teach the next coordinator how to make this decision.”

Request-derived essentials:

## Strong objections, smallest experiment and stopping

The strongest objection is C: it already tested technical translation without a brevity constraint and tied satisfactorily. D changes the decision structure/domain, not the established fact that this baseline often communicates well. E resembles prior generated-work cases in important respects; its distinct diagnostic contribution is the actual decision boundary. Neither proposal warrants another run merely because it is new. Removing W1's chat instruction is a coverage change, not evidence that a better plugin mechanism exists.

First require the separate mechanism diagnosis to supply a meaningfully different, evidence-backed candidate. If it cannot, **stop without subjects**. If it can, the smallest response experiment is the complete frozen D absent/enabled pair: two conversations, six task starts, same supported host/model/effort/tools/audience. Freeze candidate, fixtures and root's gate before dispatch; do not run untreated scouting and then tailor enabled instructions. Review every observed reply and preserve requested D3 depth.

If untreated D is already satisfactory on the targeted final goals and enabled adds no concrete benefit, record that ceiling and stop this proposed expansion. If enabled loses precision/depth, worsens a goal or simply reproduces the targeted defect, stop rather than retry or shop for a weaker baseline. A genuine useful final improvement can justify the predeclared disabled control and E work/boundary comparison; it does not itself prove progress improvement or generalization. Root must record any continuation allocation and obtain the existing qualified independent reviews of all saved evidence. A setup/provider/capture problem remains a problem, with no automatic replacement.

An important E1 decision or E2/E3 work loss rules out full success even with shorter chat. If no natural progress opportunity occurs, mark that goal untested; do not force one or declare it cured. A small favorable development comparison still leaves repeatability, other hosts/models, actual desktop behavior and untouched validation unresolved. Another satisfactory tie justifies stopping this hypothesis, not degrading the baseline or weakening the success criteria.
