## Evidence and limits

The installed experimental package is four files, installed through the native marketplace/plugin controls in disposable profiles. Its command hook reads its colocated `policy.txt` and returns SessionStart `additionalContext`. [Official hooks documentation](https://learn.chatgpt.com/docs/hooks) defines that output as developer context. Its name does not make it a replacement system prompt. The existing pinned 0.163 hook runtime records this context as conversation items; current native protocol schemas identify public hook status and message phases. These describe delivery mechanisms, not semantic adherence.

The independent continuing instruction challenger inspected the eight A/B enabled development subjects e04/e05/e08/e09/e13/e14/e15/e16. Each saved conversation has one complete byte-equivalent authored policy as a **developer** message before the initial simulated-human task. Root separately inspected e14's exact developer message and its following three user turns. This is stronger evidence than installation or a successful command alone. The old root-policy subjects are being reconciled in the independent report. Raw session files and host instruction bodies remain local; only selected role/order/hash facts belong in public evidence. No hidden reasoning or opaque child directive is inspected.

The policy remains in each inspected same-conversation history before later user requests. No compaction was observed in those inspected records. Persisted model-conversation context is observable; exact outgoing requests and attention/adherence at every follow-up are not. Compaction/restart/fork durability is not established by these short runs. The current startup-only matcher must not be described as tested durable activation after compaction.

Manual e06/e10 comparators are configuration-supplied instructions, explicitly recorded as `minimal`; they are not installed-plugin evidence. New e31 is absent and contains no candidate. Its supported history records the generic host instruction hash as a developer message and no external instruction-source file. The new backend's enabled delivery still needs its own actual record if an enabled trial is warranted.

## Hypotheses under examination

The active host text requires an opening tool-work message and ongoing updates during longer work. It also directs concise, useful communication, so it is not a blanket requirement for verbose replies. A plugin that preserves host requirements cannot promise silence; the content of an accurate required update may still be needless for the reader. No host prompt or requirement is removed or replaced here. The observed role/order does not reveal the entire upstream system layer or settle every potential conflict.

The old audience rules deliberately exclude unclear audiences, genuine machine output, protected deliverables and inter-agent traffic. They do **not** expressly exclude all automated executions. Every matched development arm receives the same explicit preamble identifying ordinary replies as addressed to a simulated human. JSON is the capture envelope, not the requested conversational answer. Omission of that preamble is not supported by inspected historical records. Model audience classification remains unobservable; conservative wording could still misfire, which is a hypothesis rather than a confirmed explanation for ties. Preserve the exemptions and do not label every user-role message human-directed.

Captured agent-message items are model-written progress/final messages. Tool activity cards, native banners, spinners and desktop notifications are different surfaces. This experiment records public backend messages and their receipt times, not the user's notification experience. Same backend/model/effort improves representation but does not make the isolated API client identical to this long-lived desktop chat.

## Launch decision

Keep the active absent trial unchanged. Before a new enabled launch, finish its actual-chat/actual-file assessment and the independent delivery inventory, then decide whether it reproduces unnecessary reading. Any confirmed delivery/audience defect pauses affected launches and requires a separately retained correction/comparison; old outputs remain valid historical observations with their limitations. Do not infer that all ties prove ineffectiveness or explain them away. No new policy is justified by installation metadata alone.
