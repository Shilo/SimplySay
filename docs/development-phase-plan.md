# Experimental development phase: proposed scope and allocation

Date: 2026-10-29. Status: **local preparation authorized; additional model conversations await owner approval**. This supersedes the earlier direction to close the pilot, not its historical policies, criteria or results. The previous 24/24 allocation is exhausted. No new subject, helper, reviewer or diagnostic has been launched for this phase.

The goal is a working experimental candidate that reduces unnecessary reading and interruptions while retaining essential information and full work. Installation convenience is useful but cannot establish this communication benefit. Production architecture, final marketplace identities and publication remain unapproved. Release testing remains separate under the existing [product checklist](product-completion-checklist.md).

## One recommended allocation: at most 32 additional conversations

There are **30 scheduled slots and two failure reserves**, not 32 automatic launches. Counts include independent built-in agents, native subject roots, unexpected children, startup failures, diagnostics and replacements. No direct Claude execution, paid API judging, new paid service, global installation or personal project access. Use existing Codex subscription access and the previously approved temporary-cache handling only in disposable local profiles; remove each copied sign-in cache afterward. Stop if additional charges or broader access would be required.

Subjects have delegation disabled; the two challenge agents and four reviewers must not spawn or call models.

Keep explicit same-ID follow-ups rather than resetting context between turns. Draft development lengths are three, four and three turns; each holdout is four turns. This schedules 88 native subject turns. Each challenger may receive at most three task turns, each development reviewer two, each holdout reviewer one: at most 100 scheduled model turns. A reserve conversation has at most four turns, giving a hard maximum of 108 turns as well as 32 conversations. If a continuation creates another ID, it consumes another conversation slot; it is not hidden as a follow-up. ## Development sequence and independence

1. Preserve the current tracked evidence by hash; prepare the [diagnosis](development-diagnosis.md), two new candidate drafts and neutral development requests locally. These are controller-authored proposals, not independently reviewed or tested policies.
2. **After allocation approval**, reserve and start the two real challenge agents. The instruction challenger sees policies and existing evidence, but no sealed holdout content. The case/evaluation challenger sees neutral task drafts, original requests and capture/review tools, but not candidate policies, treatment outputs or preferred outcomes. It challenges overly exhaustive rubrics and seals the two holdouts and their checks before development outputs exist. Record hashes and leave their contents unread by candidate developers until the selected policy is frozen.
3. Resolve pretrial defects offline where possible. Reuse the existing Codex client, native package/trust workflow, event exporter, actual-file snapshots, review schema, four calibration controls, strict validator/scorer and format adapter. Adapt these tools and data for this phase; do not build another framework, service or generalized runner. Keep historical tools and evidence unchanged. Freeze each batch's requests, fixtures, task-derived requirements, policy/package bytes, code, execution order and allocation before its subjects.
4. Run the first eight development cells, retaining every event, failure and actual file. Two blinded reviewers assess this batch. They do not see policy text, treatment labels, reveal maps or each other's judgments. Screen candidate A's relevance/interrupt gate against B's incremental-conversation approach and the old simple instruction; do not repeatedly rescore the old 192-word policy.
5. Use those development findings to select or revise **one** compact candidate once. Explain the general observed problem addressed; do not add individual case facts or a growing list of exceptions. Freeze that version and unchanged alternatives before the four validation cells. The same development reviewers review the new batch with fresh aliases and reversed ordering, using the same dimensions. Retain initial calibration failures; a later favorable review cannot erase them.
6. Select one promising exact version for holdout testing using all development outcomes, preservation failures and uncertainty. If no version is worth testing, stop early rather than use holdout slots on a foregone or unreviewable comparison. Freeze the selected policy before opening the sealed conversations. Make **no** policy, case, essential-check or threshold changes after opening them. Unusable holdout evidence remains missing; do not replace an unfavorable case.
7. Run the eight holdout cells and the four fixed absent/enabled repetitions in a precommitted counterbalanced order. Each installed-disabled arm contains the exact selected package, effectively disabled before a fresh conversation starts; it is not an empty directory described as an installation. Validate loading and scope separately from response quality.
8. Two fresh blinded reviewers assess all holdout results; each receives opposite side assignments and case/pair order. Retain every tie, disagreement, shared error, failed check and missing capture. Stop and report the decision and remaining limitations. No production implementation, naming or publication follows automatically.

## Cases and request-derived preservation

[Development drafts](../experiments/development-v1/cases.development.draft.json) cover an operational decision with state-changing follow-ups, a real small code repair with tests and documentation, and a substantial technical explanation with an operational document. They include already-clear questions as well as opportunities for unnecessary explanation, jargon, repetition and progress narration. No request asks a subject to be verbose, imitate a bad response, obey a SimplySay development file, delay artificially or generate extra updates.

The independent case agent finalizes launchable fixtures and checks. Every essential must point to an actual request clause or explain why it is necessary to prevent a materially misleading answer. Separate chat essentials, standalone artifact essentials, exact-copy obligations and optional useful context. Do not turn all available source facts, all hypothetical consequences or every arithmetic restatement into mandatory coverage. Correct equivalent forms count; later answers do not repair earlier requested deliverables. Shared errors are failures but are not automatically instruction-caused regressions.

Use a realistically larger repair task and multi-turn changes rather than artificial sleeps or tool-count requirements. Keep actual elapsed timestamps if the existing capture can record them with a small local change; otherwise disclose missing cadence. Do not claim the CLI represents desktop behavior. Do not strip the host's default writing/progress instructions or add verbosity to the baseline. Natural short baselines remain in the cohort and may properly tie.

## Separate decision rules, recorded before subjects

**Information and work:** actual requested behavior and essential facts must remain correct, appropriately qualified and complete at the requested turn. Inspect and, where appropriate, execute actual generated code with frozen black-box checks in the isolated project. Inspect actual tests, documentation, copy-ready text, structured outputs and retained source files; text length is not a work-preservation test. A policy-specific essential omission, misleading certainty, incomplete requested explanation, reduced verification or inappropriate shortening of a protected deliverable blocks a favorable candidate recommendation until addressed in development and independently checked. Shared baseline errors remain failures; report their consequence rather than implying causal regression or deleting the cell. Any unresolved material preservation failure in the selected version's holdout outputs prevents a qualification claim. Missing evidence is unverified, never passing.

**Communication:** use the existing separate clarity, relevance, filler, repetition, unnecessary-jargon and excessive-update judgments. A win needs a quoted, request-specific improvement, not fewer words or messages alone. A factual progress update still needs a reader benefit: a necessary decision, blocker, material finding/change, meaningful expectation or required host notification. Do not suppress timely approvals, warnings, uncertainty, a request for status, or necessary wait information. Useful technical terminology and substantial requested reasoning are not defects. Count baseline and disabled flaws too; do not call a tie success or failure without diagnosing it.

**Repeatability:** a provisional communication recommendation requires both calibrated holdout reviewers to prefer enabled to absent in **at least three of the four preplanned matched case/repetition pairs**, with a specific unnecessary-reading or interruption defect reduced. At least one agreed improvement must occur on each of the two conversations; no pair may have an agreed material communication regression. For an interruption-reduction claim, at least one matched improvement must concern avoidable progress interruptions, not final prose alone. If only wording improves, report that narrower result and leave interruption reduction unestablished. Retain all four pairs in the denominator, including clear baselines, failures and disagreements. Report missing/uncalibrated reviews and material differences from disabled; do not pool comparisons to manufacture a win. This is a small automated development check, not statistical proof or measured human comprehension.

**Controls and convenience:** reuse the four existing omitted-essential, filler/update, useful-depth and identity controls without weakening their expectations. They validate the assessors, not the candidate's efficacy. Manual simple instructions need not lose: equivalent communication can support choosing a convenient package **only if** a communication benefit over natural absent responses is independently established. Native Concise remains unavailable/deferred unless availability is verified within scope; do not invent it or spend an unallocated session searching for it.

## Known blockers and boundaries

- The original incoming native parent-to-child instructions remain **unverified**. Do not repeat the blocked capture test, decrypt private traffic or introduce another delegation setup. Inspect available actual returned messages and retained reports, but do not turn those into a complete inter-agent scope pass. The owner has not approved a new verification route.
- Cached host instructions require opening/periodic updates; the exact effective precedence in a new run is not established by that cache alone. Preserve stock matched host settings and investigate this constraint before attributing residual interruptions to weak policy. If the host prevents the requested reduction, report the limitation and discuss it before a different architecture or access route.
- New experimental packages contain only the compact policy and necessary local loading files. No evaluator, model call, rewriting service, telemetry, development instructions or extra runtime work is installed. No permanent preference override.
- Cross-host scope is preserved as a requirement, not claimed as demonstrated. Claude remains owner-run/deferred; no direct command, sign-in probe or paid use is authorized. Marketplace acceptance and technical feasibility remain separate questions.
- Necessary release compatibility, scope, install/upgrade, disable/remove, privacy/full-history and licensing checks remain open in the 17-item product checklist, with a separate scope and budget to agree before release work.
