## Representative matched observations

The already-clear last question asks when a 3:00 pm, 20-minute restore check ends. Absent says “Be available at **3:20 pm**, when the restore check should finish.” Enabled says “Be available at **3:20 pm** to check the restored files.” That is an acceptable tie, not a missing opportunity to compress harder.

For the requested technical explanation, absent starts “Reconciliation groups rows by record_id, then chooses the highest numeric revision within each group.” Enabled starts “record_id identifies a work order. A title is just a field, so matching titles do not make two rows the same work order.” Both then work through complete rows, revision ties, first-ID order and regression coverage. Neither reviewer finds a material readability difference.

Progress still contains examples such as absent's “I’m now checking the final tests, CLI output, and hashes of the three protected files” and enabled's “I’m adding regression tests for those requirements and the CLI.” Reviewers consider the diagnosis and regression news useful, rather than empty status. The controller retains a narrower concern: a truthful result does not itself show why optional detail must reach the user before completion. The new short-operation control establishes recognition of extra truthful updates when no periodic message is due; it does not separately establish sensitivity to optional elaboration **inside** a required status message. This is a prospective evaluation-coverage question, not grounds to edit the current ties or invent an enabled win. Both arms can retain the same unresolved pattern.

Recorded first-repair completions include long gaps between completed authored messages in both arms. They are not exact authoring/notification timing, and required-update compliance is not established. The observed message-count difference cannot prove fewer unnecessary interruptions or a UI improvement.

## Diagnosis and next development question

The cases often provide a plain-language source or explicitly request extensive explanation, and the baseline is already clear. Installed delivery is supported; these ties do not demonstrate a loading failure or universal instruction ineffectiveness. Nor do they qualify concrete.v1 as useful.

Continue only with a different evidence-backed question: natural technical source material for a nontechnical reader can test terminology/causal explanation where the first unit supplied little headroom; a generic explicit omission of preparation/checking/finishing previews can test the residual progress pattern on the already used study workflow. Before new grading, add a prospective same-presence control for optional payload inside a host-required update. Keep old controls/results unchanged; do not use revised grading to manufacture a retrospective success. Final-answer guidance need not be rewritten merely because satisfactory answers tied.

New-phase usage: **12 attempt slots/27 task starts**: three development contexts/seven tasks, six completed response contexts/eighteen tasks, one pre-model failed attempt, two fresh reviewer contexts/two tasks. Metadata-only disabling diagnosis created no thread/model turn and copied no credential. All 26 old/new disposable profiles checked retain no copied sign-ins. Provider checks explicitly allowed included use before subject turns; no paid fallback, new service, billing change, provider bypass or Claude execution occurred. Old overall caps were superseded by the owner, not exceeded without authorization.
