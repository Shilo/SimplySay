## Smallest useful full-goal development unit

Recommend **two distinct three-turn development conversations, each run absent, installed-enabled and installed-disabled**: six response contexts, 18 response turns. Two fresh independent blinded review contexts, one task each, bring this unit to **eight contexts/20 task starts**. This is an initial development unit, not an overall cap or release validation. Record failures and diagnostic starts separately; do not hide them as free work.

Use one frozen original candidate for the unit. Other compact policies can remain unrun alternatives until an observed failure supplies a distinct question. ### Conversation A: practical explanation and decision

Three naturally connected short questions from a volunteer coordinator, using one small local notes fixture:

1. “Our shared folder syncs changes between laptops. If someone deletes a file, is that the same as losing the backup? I coordinate the volunteers and don't manage IT.” The fixture states that deletion propagates through the shared folder, a separate daily backup retains 30 days, and no restore test has yet been done. Essential answer: distinguish synchronization from a recoverable retained copy; do not promise recovery merely because a job succeeded. No exhaustive backup architecture is required.
2. “For handing these files to the next coordinator, would you rely on the shared folder, the backup, or both? What needs checking before we rely on it?” Essential answer: the shared workspace serves collaboration; the separate retained backup serves recovery; the untested restore is a material uncertainty. The actual request supports a practical recommendation, not an inventory of every possible security/disaster scenario. Equivalent justified recommendations count.
3. “The restore check starts at 3:00 pm and takes 20 minutes. When should I be available to check the restored files?” Essential answer: 3:20 pm, with no invented timezone or lecture. This retains an already-good baseline opportunity within the same conversation.

Do not tell subjects to be verbose or to demonstrate any named policy. The audience signal and all preferences are identical across conditions. A plain explanation may already be good in the absent arm; that is an acceptable tie, not a demonstration of a jargon improvement.

## Realistic additional calibration

Use small synthetic comparison fixtures, never edited response baselines. Freeze their expected defects before reviewer dispatch. Retain legacy controls for compatibility and add these targeted controls to the same packet:

| Diagnostic pair | What must be recognized |
| --- | --- |
| Truthful optional updates | Identical correct final/work and required opening; one trace adds accurate header/checking and finishing previews during a short recorded operation. No decision, blocker, changed expectation or required cadence justifies those extra messages. Prefer the other on progress content while preserving information on both. Truthfulness alone is insufficient. |
| Plausible overexplaining | Identical sufficient practical answer; one adds a coherent but unrequested architecture/history explanation and repeats its takeaway. Prefer the sufficient answer on unnecessary explanation, with quotes identifying the surplus. Do not use a bizarre unrelated fact as the only test. |
| Unexplained terminology | Semantically equivalent answers to an explicitly nontechnical requester; one relies on unexplained implementation shorthand. Prefer the explained/plain version on jargon and clarity, without treating useful precision as an omission. |
| Necessary interruption | A task explicitly requires stopping for a decision before the next action. One output clearly asks the needed question before proceeding; the mutant loses that necessary decision request. Prefer the proper interruption and mark the missing requested action as an information failure. Do not teach “fewer updates always wins.” |

The legacy requested-depth control supplies a counterexample where the longer causal answer is better; keep that request and its information burden. Also retain identical-output ties. Distinct correct wording passes; avoid requiring one magic phrasing in an issue field. The old raw controls and scores are not modified.

Use calibration eligibility by the claim it supports: report legacy preservation/depth eligibility and each new diagnostic result. A reviewer failing the terminology control cannot substantiate a jargon improvement merely because its overall preference is favorable. A reviewer failing a preservation/necessary-interruption check cannot supply a clean preservation pass. Retain raw all-reviewer observations alongside qualified results; do not drop failures or substitute another reviewer until a favorable count appears.

Before dispatch, locally test: unchanged-format valid review acceptance; explicit omitted-essential detection; literal evidence validation; exact pair coverage; companion/legacy choice agreement; tie-category handling; and wrong-side/missing explanation rejection. Replay packet preparation once to confirm only prospective new controls/fields changed, never historical sources. This is a small adapter contract check, not a live model test.

## Decision and stopping rules

- Record delivery, obedience and usefulness independently. Exact installed policy/context supports delivery, observed response choices support obedience, and calibrated reader-focused judgments support usefulness. None implies the other two. Host-required opening/cadence and interface notifications remain separate.
- The unit is **promising**, not validated, only if the qualified independent reviews identify a concrete useful final-answer gain where a problem occurs and a progress-content gain where optional narration occurs, without a request-derived information/work loss or a worsened communication goal. Already-clear segments may tie. If one goal had no real opportunity, mark it untested and plan a purpose-specific later case rather than claim success.
- Preserve and describe shared baseline task failures. They may leave comparative communication evidence interpretable, but they do not qualify the full work-preservation requirement. Do not repair the policy with a rule about this fixture's fields or integers.
- If installed-disabled/absent differ, inspect recorded context/configuration before attributing a style effect. If enabled has no effect, inspect delivery already available, wording adherence, audience interpretation, competing host requirements, task opportunity and calibration; do not repeat unchanged subjects by habit.
- A new version must be frozen before separate unused validation conversations and repeated matched observations. Do not tune from validation and continue calling it untouched. Existing sealed cases remain unopened during this design task; their future suitability is not assumed. Broader model/application coverage, actual desktop behavior and native inter-agent boundaries require their own justified checks, not claims from this unit.

This proposal intentionally does not equate token reduction, an overall preference, a successful hook or two friendly reviewers with the full product goal. It offers one compact development unit and the smallest visible measurement gap to correct before spending it.
