## Challenge to V5

V5's temporal gate is stronger than V4's permission for any material result: a true finding may belong in the completed answer instead of a pre-completion interruption. It is a reasonable hypothesis, not an established fix.

1. **Do not apply the timing gate to the final answer.** “Needed before completion” selects optional progress. It must not erase the completed result, a requested explanation or the uncertainty that qualifies the answer. V5's surrounding wording already separates work-time interruptions from reporting actual results; retain that separation.
2. **A consequence can still become a loophole.** The model may call every corrected number consequential or every routine check a change in expectations. Judge the actual benefit of receiving it now, not the presence of those labels. Avoid adding example-specific exceptions after each output.
3. **Protect timely communication.** A new fact invalidating advice the user may currently act on, a needed approval, a real blocker or a delay that changes expectations can merit interruption. Suppression that leaves the reader acting on stale advice is a failure even if the final later corrects it. Do not require a user action for every useful warning or wait expectation.
4. **Respect mandatory presence.** The host may require an update even when no new decision/finding exists. The candidate must not manufacture news or claim silence as a win. Keep the required message minimal; optional preparation/checking/finishing inventories are not required simply because a message is required. Receipt times alone do not establish exact cadence or UI notification burden.
5. **V5 barely changes final-answer guidance.** Its plain-language sentence is inherited. A progress win would not show that jargon, unnecessary explanation or final-answer repetition improved. Those need separate observed judgments and suitable requests.

## One original candidate to screen

Working label **R: concrete explanation**. This is a proposal for the lead to freeze, not an installed or qualified version. The shared audience and protected-work language deliberately follows SimplySay's existing contract; the new ordinary-answer mechanism is independent wording, not text copied from a reference product.

> Apply only to ordinary chat identified by host or task context as human-directed; leave unclear audiences unchanged. Answer the current question first. Use concrete actors, actions and consequences; explain unfamiliar technical terms when needed, preserving precision. Include reasons and context that make the answer understandable and usable; omit background or recaps that add no understanding. Retain requested depth, uncertainty, warnings and approvals. Keep host-required openings and cadence brief; otherwise interrupt only for information needed before completion. Preserve required content, detail and format in copy-ready text, quotations, files, code, documentation, structured output, tool traffic, memory and inter-agent messages. Complete all work and verification; report actual results honestly. Honor explicit user preferences.

The distinguishing mechanism is **positive construction of an understandable explanation**: concrete referents/causal links and reader-appropriate terminology. This is different from a fixed length cap or merely asking the model to delete more text. Its relevance clause overlaps prior A/B policies; no novelty or efficacy is claimed for that clause. The temporal progress gate is retained as a separate hypothesis rather than expanded into another long rule list.

Risks: unnecessary definitions can add clutter for an expert; “concrete” can oversimplify useful abstractions; an aggressive background filter can remove a prerequisite; the progress wording can still be ignored or classified broadly. Requested knowledge/depth, precision and timely warnings constrain those risks but do not prove protection. If an observed failure calls for rewriting, change the mechanism rather than adding a fixture-specific noun or exception.

Shared baseline correctness defects remain failures without automatically being attributed to the policy. |

Keep delivery, obedience and usefulness separate in the report. For a changed candidate, bind its installed bytes and supported model-visible text through the existing mechanism; do not repeat established installation investigations or infer attention. Then inspect actual chat for the intended changes. Finally ask blinded reviewers whether those changes help the reader without showing the candidate text. Literal policy obedience is not a usefulness score.

Use the already existing natural absent/installed-enabled/installed-disabled comparisons and factual human-audience preamble identically across arms. Do not add style reminders only to the treatment. Development may revise the candidate; untouched validation must remain separate and must include repeat observations before a reliability claim. A failed grader format can be recovered only when its existing explicit meaning can be preserved, as already documented; absent substantive judgments stay unknown.

I do not recommend a second new candidate or a broader prompt search until the first matched outputs reveal whether the concrete-explanation mechanism changes behavior. If it shows no effect, inspect the actual language, applicability and competing guidance before spending repetitions. If the baseline is adequate on a goal, record that tie; if both still have the defect, retain the unsolved result. No current evidence supports universal obedience, comprehensive scope isolation, another-host compatibility or production promotion. Original unreadable child directions remain unverified.
