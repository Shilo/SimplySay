## Why change the experiment

The actual complained-about project workflow includes sustained research and procedural narration. Most local CLI subjects were already clear, and neither compact mechanism/revision yielded a consistent agreed benefit over absent. Loading evidence passed, while actual application/host effects remain partly uncertain. Repeating those same comparisons is unlikely to answer whether the product can solve the owner's reading burden. Use the actual visible workflow examples to design neutral longer tasks, without planting verbose responses, asking for verbosity, adding fake delays or stripping genuine existing preferences.

## Scope changes needing an explicit decision

This moves four original final-comparison slots into development. **Fresh selected-version installed-disabled and manual-instruction final comparisons would be deferred to separately budgeted installation/lifecycle/release testing.** Their requirements are not dropped and no passing result is claimed. Existing manual and disabled evidence remains bounded by its tested versions. Absent/enabled final repetitions retain the primary efficacy comparison; the plugin need not outperform identical manually supplied guidance. If this deferral is unacceptable, do not silently narrow the tests or launch this allocation.

The deferred manual comparison is an efficacy/substitutability check, not merely installation housekeeping. The deferred disabled comparison tests exact-package behavioral controls as well as lifecycle behavior; neither is established by a static file check alone.

The original provisional final rule demanded wins in at least three of four case/repetition pairs and at least one on each conversation. This is a stricter breadth requirement: an already-clear case may legitimately tie and prevent qualification without showing regression. That does not invalidate the benchmark. **Keep that benchmark unchanged and report it explicitly.** Repeated benefit confined to a narrower task can be described with its limits, alongside unchanged clear replies; it is not silently relabeled as meeting the broader gate. If a different qualification claim is wanted, obtain an explicit prospective decision before opening the sealed cases or seeing their outcomes. No retrospective waiver or changed score is proposed.

## Development controls

- Use the existing tools and observed-work checks. Keep actual source, tests, documentation, structured/copy-ready outputs and available inter-agent work complete. A shared baseline error still fails the task; it does not alone establish a policy-caused regression. Do not add domain-specific instruction exceptions.
- Freeze both new cases, fixtures, request-derived essentials, artifact checks and baseline-burden gate before their absent subjects. Do not rewrite or resample cases until they produce clutter. Preserve genuine existing user preferences and clear baselines.
- The instruction challenger examines actual baseline burden and general mechanism before enabled subjects; policy developers do not see final sealed content. The development reviewers remain treatment-blinded and receive no preferred winner. Already-clear baselines may tie; no instruction to be verbose or forced routine-update count.
- Match available Codex host/settings and identify what is actually simulated. Current desktop model/effective prompt is not yet established; a similar workflow is not proof of full desktop compatibility. Investigate loading/configuration locally first, without new model diagnostics where static checks suffice.
- No new delegation route, blocked native-capture retry, permanent preference override, extra runtime model call, evaluator, rewriting service or production adapter is authorized by this proposal.
- Stop if the new baseline route still does not reproduce the complaint, the revision is not promising, evidence is missing, or existing account limits require charges/expanded access. Preserve all outcomes, ties and disagreements. Do not automatically start another round.

Compatibility, full scope preservation, exact installation/upgrade, enabled/disabled/absent behavior, removal, licensing/privacy/full-history review and exact release approval remain in the unchanged [17-item product checklist](product-completion-checklist.md), with a separately agreed release scope/budget.
