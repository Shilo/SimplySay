# What the current development route failed to reproduce

The development go/no-go gate was not met. Both calibrated reviewers tie every A/B version against absent in the code scenario. In the operations scenario, one reviewer finds modest framing improvements and the other ties; neither version earns an agreed clutter/interruption improvement. A v3 emits only its opening update in the repair, but both reviewers still tie its overall communication with absent. Fewer messages alone is not a quality result. No final holdout, repetition, fresh disabled comparison or final reviewer was launched.

This is a specific evidence gap rather than proof that every instruction is ineffective. The simulated operations answers are already direct, their follow-up explicitly requests the technical terms, and the repair's substantial explanation is requested. There is little consensus filler or unnecessary jargon. One reviewer regards the repair's causal diagnosis as useful transparency; the separate instruction challenger sees a possible interruption that could wait for completion. That disagreement remains real. Native loading/bytes/continuation checks passed and generic cached host-template hashes match across all 12 profiles, which makes a simple missing-file explanation less likely. It does not prove model attention, exact effective instruction priority or reliable audience classification. Required opening/periodic updates can impose a floor, but do not explain every tie or automatically make update content useful.

The owner complained about the current project's longer research/evaluation workflow. A read-only inspection of this exact project chat, identified from current process context and verified by the existing app connector, recovered the human-visible progress sequence around that complaint. No other chat/project was opened. One oversized request failed; a smaller message-summary request succeeded. Only public user/assistant message fields were selected; reasoning, tool arguments and private output were excluded and not saved. This retrieval started no model conversation.

[complaint-context.json](../experiments/development-v1/complaint-context.json) records the private input's hash and workflow patterns. Every available progress message from that returned historical turn, the necessary approval question and the owner's feedback are retained in the ignored `.local/complaint-context.private.json`; verbatim project-chat excerpts are not release files. Examples include reporting that an evaluation amendment was committed, reciting frozen calibration rules, and announcing that reviewer jobs were being prepared. These describe genuine work, but mostly add procedure/state the person need not act on. The same sequence also contains a real evidence blocker and an approval question about the encrypted delegation route; those are materially different and must remain timely. Do not retroactively claim that every earlier message violated a preference not yet expressed, or classify every genuine finding as filler.

This source is **workflow-style evidence**, not an extra neutral absent trial, a new blinded score or a complete source for information-preservation grading. Task summaries may be truncated; per-message cadence and exact desktop model/effective prompt are unavailable. It demonstrates that the complained-about workflow includes sustained research and administrative narration not well represented by the short local operations/repair subjects. It does not prove that desktop versus CLI alone causes the difference. The source feedback, current independent judgments and possible instruction/host limitations should all shape the next experiment.

Recommendation: do not promote a candidate or keep resampling unchanged instructions on these mostly clear cases. First reproduce the specific workflow burden in neutral, authentic longer requests, retaining any genuine request for brief replies, approvals and depth. Confirm actual baseline clutter before testing another general compact revision. Keep actual code/files/copy-ready work checks and the existing blinded tools; no new framework or runtime rewriting service is needed. A proposed reallocation is in [development-next-allocation.md](development-next-allocation.md); it is not authorized merely because 16 conversations remain unused.

The two final sealed conversations remain unopened and unchanged. Original incoming native child instructions remain unverified. The shared timestamp-contract defect remains a work failure across conditions, not a concision-caused regression. Production architecture, marketplace identities and publication are still on hold.
